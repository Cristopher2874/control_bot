# T1.2: Core, config y proveedor Ollama

- **Fase:** 1
- **Estado:** Pendiente
- **Depende de:** T1.1

## Objetivo

El harness puede cargar perfiles de modelo desde `config/models.yaml` y mandar una conversación a Ollama a través de un `ModelProvider`, sin CLI ni telemetría todavía.

## Contexto mínimo

- **Nada se instancia al importar.** Ningún módulo crea clientes, lee config ni abre conexiones a nivel de módulo. Todo se construye en funciones o en el composition root (T1.3).
- **`core`** son dataclasses puras (sin I/O, sin dependencias externas): `Message(role, content, tool_calls=None)`, `ToolCall(name, arguments: dict)`, `ModelResponse(message, model, prompt_tokens, completion_tokens, latency_ms)`. `Task`, `Run` y `Event` se agregan cuando una tarea los use.
- **Perfiles de modelo** (`config/models.yaml`): cada perfil tiene `model`, `locality: local | cloud`, y opcionales `num_ctx`, `temperature`, `supports_tools`. Un perfil `default` apunta a uno local. Perfiles iniciales:

  ```yaml
  default: standard
  profiles:
    light:    { model: gemma4:e2b,       locality: local, num_ctx: 8192 }
    standard: { model: gemma4:e4b,       locality: local, num_ctx: 8192 }
    fast:     { model: llama3.1:8b,      locality: local, supports_tools: true }
    cloud:    { model: gemma4:31b-cloud, locality: cloud }
  ```

  Ollama sirve los modelos cloud por el mismo daemon local, así que **`locality` se toma del perfil, nunca de la URL**.
- **Settings** con pydantic-settings: `ollama_url` (por defecto `http://localhost:11434`), `request_timeout_s`, ruta a `config/`. Prefijo de variables de entorno `HARNESS_`.
- **Proveedor:** `ModelProvider` es un `Protocol` con `chat(profile, messages, tools=None, format=None) -> ModelResponse`. `OllamaProvider` usa `httpx` contra `POST /api/chat` con `stream: false`. No usar LangChain ni el SDK `ollama`: control directo de la petición.
- **Alias:** el bot viejo tenía alias de modelos en `legacy/app/config/` (u otro archivo de config). Rescata los que sigan sirviendo como nombres de perfil.

## Alcance

**Incluye:**
- `harness.core`, `harness.config`, `harness.models` (Protocol, `OllamaProvider`, `FakeProvider` para tests).

**Fuera de alcance:**

## Pasos de implementación

1. Dependencias de `harness`: `pydantic`, `pydantic-settings`, `pyyaml`, `httpx`.
2. Dataclasses de `core` (`frozen=True` donde tenga sentido).
3. `load_profiles(path) -> Profiles`: valida con Pydantic, error claro si `default` apunta a un perfil inexistente o si falta `locality`.
4. `OllamaProvider(settings, client: httpx.Client | None = None)`: arma el payload (`model`, `messages`, `options` con `num_ctx` y `temperature`, `tools`, `format`), mide latencia, lee `prompt_eval_count` y `eval_count`. Errores de conexión → excepción propia `ProviderError` con mensaje útil ("¿está corriendo Ollama?").
5. `FakeProvider`: devuelve respuestas predefinidas y guarda las llamadas recibidas (lo usarán T2.1 y T3.x).

## Output esperado

Desde Python: `OllamaProvider(...).chat(profiles["standard"], [Message("user", "hola")])` devuelve un `ModelResponse` con texto, tokens y latencia.

## Tests mínimos

- `test_profiles.py::test_load_profiles_valido`: carga `config/models.yaml` real y el `default` resuelve a un perfil local.
- `test_profiles.py::test_perfil_sin_locality_falla`: un YAML sin `locality` da error de validación.
- `test_ollama_provider.py::test_payload_y_parseo`: con `httpx.MockTransport`, verifica que el payload lleva `model` y `options.num_ctx` del perfil, y que la respuesta se convierte a `ModelResponse` con tokens.
- `test_ollama_provider.py::test_hola_real` (`@pytest.mark.ollama`): llamada real al perfil `default`.

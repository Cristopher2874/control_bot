# T1.3: Telemetría y `harness chat`

- **Fase:** 1
- **Estado:** Pendiente
- **Depende de:** T1.2

## Objetivo

`uv run harness chat "hola"` responde con un modelo local y deja una traza JSONL del run. Con esto se cumple el criterio de terminado de la Fase 1 (junto con T1.4).

## Contexto mínimo

- **Composition root único:** `harness.bootstrap.build_app(settings) -> App` arma settings, perfiles, proveedor, bus de eventos y telemetría. La CLI lo llama una vez; nadie más construye estas piezas.
- **Bus de eventos mínimo:** `EventBus` síncrono con `subscribe(handler)` y `publish(event)`. `Event` es una dataclass en `core` con `type`, `trace_id`, `ts`, `data: dict`. La telemetría es un suscriptor. La cola de jobs llega en T5.1; aquí no.
- **Un run:** cada `chat` es un run con `trace_id` nuevo (uuid4 corto) guardado en un `ContextVar`, para que cualquier evento lo tome sin pasarlo a mano.
- **Trazas:** `.harness/traces/AAAA-MM-DD.jsonl`, una línea por evento. Eventos de esta tarea: `run_started`, `model_call`, `run_finished`.
- **Qué se registra en `model_call`:** perfil, modelo, `locality`, `route_reason`, latencia, tokens de entrada y salida. **No** el texto del prompt ni de la respuesta.
- **Enrutamiento en Fase 1:** no hay política todavía. Se usa el perfil `default` (`route_reason: "default"`). `--profile <nombre>` permite elegir otro (`route_reason: "user_override"`).
- **Rescate de `legacy/`:** el bot viejo tenía `trace_id` con ContextVar, redacción de secretos y una allowlist de módulos para el logging. Reutiliza las ideas, no el código tal cual. Ojo con un bug conocido: hacía `chat_id_var.set(trace_id_var)`, pasando el ContextVar en vez de su valor.
- **CLI:** `typer`. Comando `harness` con subcomando `chat <mensaje> [--profile]`. Imprime la respuesta y, en una línea atenuada, modelo, latencia y `trace_id`.

## Alcance

**Incluye:**
- `harness.telemetry` (escritor JSONL, redacción, ContextVar del trace).
- `harness.runtime.events` (bus mínimo) y `harness.bootstrap`.

**Fuera de alcance:**
- Métricas de hardware, streaming en la terminal, historial de conversación (T4.x), `--lab` (T1.4).

## Pasos de implementación

1. `redact(data)`: enmascara valores de llaves sensibles (`token`, `api_key`, `authorization`, `password`, `secret`) y patrones obvios (tokens tipo `sk-…`, `Bearer …`, token de bot de Telegram `\d+:[\w-]{35}`). Se aplica a todo evento antes de escribir.
2. `JsonlTraceWriter(dir)`: suscriptor del bus; crea el directorio cuando escribe la primera vez, no al importar.
3. `bootstrap.build_app()`: arma todo y devuelve un objeto `App` con `chat(message, profile=None) -> ModelResponse` que publica los tres eventos.
4. CLI: errores del proveedor se muestran en una línea legible, sin traceback, con código de salida distinto de 0.

## Output esperado

```text
> uv run harness chat "hola"
¡Hola! ¿En qué te ayudo?
gemma4:e4b · 2.8 s · trace 3f9a1c2e
```

Y una línea por evento en `.harness/traces/<hoy>.jsonl`.

## Tests mínimos

- `test_telemetry.py::test_redaccion`: un evento con `api_key` y un `Bearer xxx` en el texto queda enmascarado en el JSONL.
- `test_cli_chat.py::test_chat_escribe_traza`: con `FakeProvider` inyectado en `build_app` y `tmp_path` como directorio de trazas, `CliRunner` ejecuta `chat "hola"`: imprime la respuesta y el JSONL tiene `run_started`, `model_call` y `run_finished` con el mismo `trace_id`, y `model_call` no contiene el texto del mensaje.
- `test_cli_chat.py::test_chat_real` (`@pytest.mark.ollama`): el comando real responde con exit code 0.

## Criterios de aceptación

- [ ] `harness chat "hola"` responde con un perfil `local` y deja la traza.
- [ ] Ningún evento contiene el texto del prompt, la respuesta ni secretos.
- [ ] Si Ollama no está corriendo, el mensaje de error es claro.
- [ ] pytest pasa sin Ollama.

# T3.1: Política y router por reglas

- **Fase:** 3
- **Estado:** Pendiente
- **Depende de:** T1.3 (y T2.4 si ya existe, para reemplazar su regla fija)

## Objetivo

Un único `Router` decide el perfil de cada llamada al modelo según `config/policy.yaml`, con reglas deterministas de sensibilidad, y un guardia impide que algo marcado `private` llegue a un perfil `cloud`.

## Contexto mínimo

- **Todas las llamadas al modelo pasan por el router.** Reemplaza el perfil `default` fijo de T1.3 y la regla `capability_private` de T2.4. Nadie más elige perfil.
- **Estado del run:** `RunContext` con `sensitivity: public | private | unknown`, compartido por todo el run. Una vez `private`, no vuelve atrás (la contaminación completa llega en T3.2).
- **Reglas** (`policy.yaml`): patrones que marcan `private` el texto del usuario. Correos, teléfonos, rutas de Windows (`C:\…`, `%USERPROFILE%`), coordenadas, direcciones, palabras como "mi ubicación", "mi casa", "mis archivos", "contraseña". Si ninguna regla coincide, `unknown` (no `public`): el clasificador de T3.2 decide; mientras no exista, `unknown` se trata como `private`.
- **Política:**

  | Sensibilidad | Tarea | Destino |
  |---|---|---|
  | private | cualquiera | local |
  | unknown | cualquiera | local |
  | public | pesada | cloud |
  | public | ligera | local |

  "Pesada" por heurística configurable: largo del texto y palabras clave ("analiza", "resume este documento", "explica en detalle").
- **Override:** `--profile cloud` solo se respeta si el run es `public`. Si es `private`, se rechaza con un mensaje claro y `route_reason: "override_denied_private"`.
- **Guardia:** `GuardedProvider` envuelve al proveedor y lanza `PrivacyViolation` si recibe un perfil `cloud` con un `RunContext` no `public`. Es la segunda línea de defensa: si el router tiene un bug, la llamada no sale.
- **Cada decisión** queda en la traza con su motivo, por ejemplo `rule:email`, `heavy_public`, `unknown_default_local`.

## Alcance

**Incluye:** `harness.router` (reglas, heurística de peso, decisión), `RunContext`, `GuardedProvider`, `config/policy.yaml`, integración en `chat` y `run`.

**Fuera de alcance:** clasificador con LLM y contaminación por salidas de tools o memoria (T3.2).

## Pasos de implementación

1. Cargar y validar `policy.yaml` (Pydantic).
2. `classify_by_rules(text) -> Sensitivity, matched_rule`.
3. `Router.decide(ctx, text) -> Decision(profile, reason)`.
4. `GuardedProvider` y su integración en `build_app`.
5. Sustituir las elecciones fijas de perfil.

## Output esperado

- `harness chat "explícame en detalle la transformada de Laplace"` → local con `unknown_default_local`. Irá a cloud cuando el clasificador de T3.2 lo marque `public`.
- `harness chat --profile cloud "mi correo es x@y.com"` → rechazado.

## Tests mínimos

- `test_router.py::test_reglas_marcan_privado`: tabla de ~10 frases (correo, ruta, ubicación…) → `private`.
- `test_router.py::test_unknown_va_a_local`: sin coincidencias → perfil local.
- `test_router.py::test_override_cloud_negado_si_privado`.
- `test_router.py::test_guardia_bloquea_cloud`: llamar directamente a `GuardedProvider` con perfil `cloud` y contexto `private` lanza `PrivacyViolation` y el proveedor interno no recibe nada.

## Criterios de aceptación

- [ ] Ningún módulo fuera del router elige perfil.
- [ ] Lo privado y lo dudoso van a local.
- [ ] El guardia bloquea cualquier llamada cloud con contexto no público.
- [ ] Cada `model_call` tiene `route_reason`.

## Telemetría

- Nuevo `route_decision`: sensibilidad, regla que coincidió (nombre, no el texto), peso, perfil, motivo.

## Seguridad

- Esta tarea es de seguridad. Ante cualquier error al evaluar la política, decide local.

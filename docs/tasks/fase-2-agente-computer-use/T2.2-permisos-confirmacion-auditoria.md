# T2.2: Permisos, confirmación y auditoría

- **Fase:** 2
- **Estado:** Pendiente
- **Depende de:** T1.4, T2.1

## Objetivo

Las tools de una capability se registran con su función Python y se ejecutan a través de un executor que aplica el nivel de permiso, pide confirmación, respeta dry-run, kill switch y límites, y deja log de auditoría.

## Contexto mínimo

- **Del manifest a la función:** el paquete de una capability expone `tools() -> list[Tool]`, donde `Tool` = `ToolDef` (T2.1) + `fn(args_model) -> str`. El registry (T1.4) cruza cada `Tool` con su entrada del manifest y falla si hay una tool sin declarar o una declarada sin función.
- **Niveles:**

  | Nivel | Comportamiento |
  |---|---|
  | `read` | Se ejecuta sin preguntar. No se audita. |
  | `act` | Se ejecuta y se audita. |
  | `dangerous` | Pide confirmación siempre. Si se niega o no hay terminal interactiva, no se ejecuta. Se audita la decisión. |

- **Confirmación** detrás de un `Protocol Confirmer.confirm(action_summary) -> bool`. Implementación CLI: `[y/N]`, por defecto no. Telegram (T5.2) tendrá la suya.
- **Dry-run:** con `--dry-run`, las tools `act` y `dangerous` no se ejecutan; devuelven "dry-run: haría X" al modelo y se auditan como `dry_run`. Las `read` sí se ejecutan.
- **Kill switch:** `CancelToken` compartido por el run. En la CLI, Ctrl+C lo activa; el loop (`should_stop`) y el executor lo revisan antes de cada acción y el run termina limpio con `stop_reason: "cancelled"`.
- **Límites:** `limits.max_actions_per_run` del manifest. Al superarlo, el executor rechaza la acción.
- **Auditoría** ≠ telemetría: `.harness/audit/AAAA-MM-DD.jsonl`, una línea por acción `act`/`dangerous` con `trace_id`, capability, tool, argumentos (redactados), resultado (`ok|error|denied|dry_run|limit`), si hubo confirmación. Es local y sirve para saber qué le hizo el harness al PC.

## Pasos de implementación

1. `Tool` y validación cruzada en el registry.
2. `Executor(registry, confirmer, audit, cancel, dry_run)` con un `__call__(ToolCall) -> ToolResult` compatible con el loop de T2.1.

4. Integración en la CLI.

## Output esperado

Con una capability de prueba en los tests: una tool `dangerous` pregunta antes de ejecutarse, y todas las acciones `act` aparecen en el archivo de auditoría.

## Tests mínimos

Con una capability falsa (tools `leer`, `hacer`, `peligro`):

- `test_executor.py::test_dangerous_negado_no_ejecuta`: `Confirmer` que responde no → la función no se llama; auditoría `denied`.
- `test_executor.py::test_dry_run`: `hacer` y `peligro` no se ejecutan, `leer` sí; auditoría `dry_run`.
- `test_executor.py::test_limite_y_cancelacion`: al pasar `max_actions_per_run` → `limit`; con el token cancelado → no ejecuta nada.
- `test_executor.py::test_manifest_y_funciones_no_coinciden`: tool sin declarar → error del registry.

## Verificación (la corre el usuario)

```powershell
uv run pytest tests/test_executor.py
```

## Criterios de aceptación

- [ ] Ninguna tool `dangerous` se ejecuta sin un "sí" explícito.
- [ ] Dry-run, límite y cancelación impiden la ejecución.
- [ ] Cada acción `act`/`dangerous` deja una línea de auditoría con su `trace_id`.

## Telemetría

- `tool_call` agrega `permission` y el resultado (`denied`, `dry_run`, `limit`, `cancelled`).

## Seguridad

- Por defecto se niega: sin terminal interactiva, `dangerous` siempre es "no".
- La auditoría puede contener datos privados: es local, está bajo `.harness/` (ignorado por git) y pasa por la redacción de secretos.

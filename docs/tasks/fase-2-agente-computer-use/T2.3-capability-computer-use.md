# T2.3: Capability computer use

- **Fase:** 2
- **Estado:** Pendiente
- **Depende de:** T2.2

## Objetivo

La primera capability real: 5 tools de computer use en Windows, con un driver real y uno simulado.

## Contexto mínimo

- **Ubicación:** `packages/capabilities/computer_use/`, nuevo miembro del workspace, registrado en el grupo de entry points `harness.capabilities`, con su `capability.yaml`.
- **Acciones tipadas, nunca shell libre.** El modelo elige una tool y rellena argumentos validados.

  | Tool | Permiso | Validación |
  |---|---|---|
  | `list_windows()` | read | — |
  | `focus_window(title)` | act | coincidencia parcial con una ventana abierta |
  | `open_app(name)` | act | `name` en `config/apps.yaml` (nombre → ejecutable o URI) |
  | `set_volume(level)` | act | entero 0–100 |
  | `run_script(name)` | dangerous | `name` en una allowlist de scripts en `config/scripts/` |

- **Driver** detrás de un `Protocol WindowsDriver` con un método por acción. Capas, de la más estable a la más frágil: 1) PowerShell/Win32, 2) UI Automation con `pywinauto`, 3) `pyautogui` solo como último recurso (en esta tarea no se usa).
- `FakeWindowsDriver` guarda las acciones recibidas en memoria y devuelve ventanas de ejemplo. Los tests y el dry-run de desarrollo lo usan.
- `data_sensitivity: private`: todo lo que devuelven estas tools es privado (títulos de ventanas, apps abiertas).
- Las dependencias de Windows (`pywinauto` y la del volumen) son solo de esta capability, no del núcleo.

## Alcance

**Incluye:** paquete de la capability, manifest, 5 tools, driver real, driver falso, `config/apps.yaml` con unas pocas apps (Spotify, Bloc de notas, navegador).

**Fuera de alcance:** workflows y el comando `harness run` (T2.4). Capturas de pantalla, visión, mouse.

## Pasos de implementación

1. Paquete, manifest y entry point.
2. Modelos Pydantic de argumentos con las validaciones de la tabla.
3. `RealWindowsDriver`: `list_windows`/`focus_window` con pywinauto, `open_app` con `Start-Process`, `set_volume` según la decisión abierta, `run_script` ejecuta solo `config/scripts/<name>.ps1` con `-NoProfile`.
4. Selección del driver en `build_app`: real por defecto en Windows, falso con `HARNESS_FAKE_DRIVERS=1`.

## Output esperado

`uv run python lab/sandbox.py` lista la capability `computer_use` con sus 5 tools.

## Tests mínimos

- `test_computer_use.py::test_validaciones`: `set_volume(150)` y `open_app("no_existe")` no validan.
- `test_computer_use.py::test_tools_con_driver_falso`: `open_app("spotify")` llega al driver falso con el ejecutable de `apps.yaml`.
- `test_computer_use.py::test_manifest_cargado`: el registry descubre `computer_use` con los permisos esperados.
- `test_computer_use.py::test_driver_real` (`@pytest.mark.desktop`, nuevo marcador excluido por defecto): `list_windows()` real devuelve al menos una ventana.

## Criterios de aceptación

- [ ] Las 5 tools existen con el permiso de la tabla y validan sus argumentos.
- [ ] `run_script` solo ejecuta scripts de la allowlist.
- [ ] Los tests por defecto no tocan Windows.

## Telemetría

Ninguna nueva (la ejecución ya emite `tool_call` desde T2.2). El driver real registra qué capa usó (`layer: powershell|uia`) en el `tool_call`.

## Seguridad

- Sin `shell=True` ni comandos armados con texto del modelo. Los argumentos van como lista a `subprocess`.
- `config/scripts/` lo llena el usuario a mano.

## Decisiones abiertas

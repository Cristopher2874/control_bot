# T2.4: Workflows y `harness run`

- **Fase:** 2
- **Estado:** Pendiente
- **Depende de:** T2.3

## Objetivo

`uv run harness run "Abre Spotify y sube el volumen"` funciona: elige un workflow, el modelo rellena los pasos, pide confirmación donde corresponde y deja traza y auditoría. Cierra la Fase 2.

## Contexto mínimo

- **Workflows antes que agentes.** Con modelos chicos, una tarea conocida es una receta fija y el LLM solo rellena huecos con salida estructurada (`ask_structured`, T2.1). El agente libre (`run_agent`) es el respaldo para lo que ningún workflow cubre.
- **Un workflow** es una lista de pasos declarada en Python dentro de la capability: `Fill(schema, instrucción)` (el LLM rellena un modelo Pydantic) y `Call(tool, args_desde_estado)` (ejecuta una tool por el executor de T2.2). El estado es un `dict` que pasa de paso a paso. Nada de grafos ni condicionales complejos.
- **Elegir workflow:** un paso `ask_structured` con schema `{"workflow": <enum de workflows disponibles> | "agent", "confidence": float}`. Si es `agent` o la confianza es baja, se usa `run_agent` con las tools de la capability.
- **Modelo:** la política de privacidad llega en la Fase 3. Mientras, regla fija: si la capability es `data_sensitivity: private`, se usa el perfil `default` (local) y `route_reason: "capability_private"`.
- **Workflows iniciales de `computer_use`:** `abrir_app` (Fill nombre de app → `open_app`) y `abrir_app_y_volumen` (Fill app y nivel → `open_app` → `set_volume`). "Subir el volumen" sin número se interpreta como un nivel relativo que el Fill resuelve a un entero.

## Alcance

**Incluye:** `harness.workflows` (pasos, motor, selector), los dos workflows, subcomando `harness run <texto> [--dry-run]`.

**Fuera de alcance:** política de privacidad real (T3.1), workflows de otras capabilities.

## Pasos de implementación

1. `Fill`, `Call` y `run_workflow(workflow, texto, app) -> WorkflowResult`.
2. Selector con fallback a `run_agent`.
3. Workflows de `computer_use`.
4. `harness run` imprime cada paso (`→ open_app(spotify) ✓`) y el resumen final.

Con `FakeProvider` y `FakeWindowsDriver`:

- `test_workflows.py::test_abrir_app_y_volumen`: el selector devuelve el workflow, los Fill rellenan app y nivel, el driver recibe `open_app` y `set_volume` en orden.
- `test_workflows.py::test_fallback_a_agente`: confianza baja → se llama a `run_agent`.
- `test_workflows.py::test_spotify_real` (`@pytest.mark.ollama` y `@pytest.mark.desktop`): el caso completo con modelo y Windows reales.

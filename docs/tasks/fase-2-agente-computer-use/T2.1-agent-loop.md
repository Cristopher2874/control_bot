# T2.1: Agent loop

- **Fase:** 2
- **Estado:** Pendiente
- **Depende de:** T1.3

## Objetivo

Un ciclo de agente propio (modelo → tool calls → ejecutar → observar → parar) y un helper de salida estructurada, robustos ante los errores típicos de modelos chicos.

## Contexto mínimo

- **Sin LangChain/LangGraph.** El ciclo es código propio (~150 líneas) sobre `ModelProvider.chat` (T1.2).
- **Formato de Ollama:** el modelo devuelve `message.tool_calls = [{"function": {"name": ..., "arguments": {...}}}]`. El resultado de una tool vuelve como mensaje `role: "tool"` con `content` (texto) y `tool_name`.
- **El loop no conoce capabilities ni permisos.** Recibe una lista de `ToolDef(name, description, args_model: type[BaseModel])` y un `executor: Callable[[ToolCall], ToolResult]`. Quien ejecuta y aplica permisos es T2.2. El schema que ve el modelo sale de `args_model.model_json_schema()`.
- **Errores que hay que absorber:** nombre de tool inexistente, argumentos que no validan, JSON inválido. Se devuelve el error al modelo como observación y se reintenta, máximo 2 veces seguidas.
- **Condiciones de parada:** respuesta final sin tool calls, `max_steps` (por defecto 6), la misma tool con los mismos argumentos dos veces seguidas (bucle), o cancelación (el token llega en T2.2; aquí se acepta un `should_stop: Callable[[], bool]` opcional).
- **Salida estructurada:** `ask_structured(provider, profile, messages, schema: type[T]) -> T` pasa `format=schema.model_json_schema()`, valida con Pydantic y reintenta una vez con el error si falla. La usan los workflows (T2.4) y el clasificador (T3.2).

## Alcance

**Incluye:** `harness.agent` (loop, `ToolDef`, `ToolResult`, `StopReason`, `ask_structured`). Eventos de telemetría.

**Fuera de alcance:** permisos, confirmación, auditoría (T2.2). Streaming. Elegir modelo (usa el perfil que le pasen).

## Pasos de implementación

1. `run_agent(provider, profile, messages, tools, executor, max_steps=6, should_stop=None) -> AgentResult(final_message, steps, stop_reason)`.
2. Validar `arguments` contra `args_model` antes de llamar al executor. Si falla, observación de error.
3. Detección de bucle y contador de reintentos.
4. `ask_structured` con un reintento.
5. Publicar eventos en el bus del `App`.

## Output esperado

Una función que, con un modelo real y una tool de prueba, resuelve "¿cuánto es 21*2? usa la calculadora" en 2 pasos.

## Tests mínimos

Todos con `FakeProvider` guionizado:

- `test_agent_loop.py::test_tool_call_y_respuesta_final`: el modelo pide una tool, recibe el resultado y responde; `stop_reason == "final"`.
- `test_agent_loop.py::test_argumentos_invalidos_se_corrigen`: primera llamada con args inválidos, la segunda válida; el executor solo se llama una vez.
- `test_agent_loop.py::test_bucle_y_max_steps`: misma llamada repetida → `stop_reason == "loop"`.
- `test_agent_loop.py::test_ask_structured_reintenta`: primera salida no valida, la segunda sí.
- `test_agent_loop.py::test_calculadora_real` (`@pytest.mark.ollama`): perfil `fast` (llama3.1:8b, soporta tools).

## Criterios de aceptación

- [ ] El loop nunca ejecuta una tool con argumentos sin validar.
- [ ] Las cuatro condiciones de parada funcionan y quedan en `stop_reason`.
- [ ] `ask_structured` devuelve un objeto Pydantic válido o lanza un error claro.

## Telemetría

- `model_call` agrega `step`.
- Nuevo `tool_call`: nombre, `ok|error|invalid_args`, latencia, **nombres** de argumentos (no valores).
- Nuevo `agent_retry` (motivo) y `run_finished` con `stop_reason` y `steps`.

## Seguridad

- Los valores de argumentos y resultados de tools no van a la traza (pueden ser privados).
